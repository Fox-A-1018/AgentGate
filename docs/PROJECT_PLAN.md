# AgentGate 项目实施路线图

基线日期：2026 年 11 月 12 日  
课程验收日期：2026 年 12 月 4 日  
当前阶段：设计成果已形成，工程实现尚待建立可验证基线

## 1 项目目标

AgentGate 要完成一条可运行、可测试、可解释的智能体工具调用安全闭环：

`结构化请求 -> 规范化 -> 权限与策略判定 -> 必要时审批 -> 凭证校验 -> 受控执行 -> 脱敏审计`

项目的核心价值不是让模型更聪明，而是确保模型只能提出候选操作，不能自行获得执行授权。

### P0 必须完成

1. 统一的 `ToolCallRequest`、`PolicyDecision`、`Approval`、`ExecutionResult` 和 `AuditEvent` 数据模型。
2. 独立网关入口，任何模拟工具都不能被 Agent 或模型适配器直接调用。
3. RBAC 工具级授权，以及文件路径、数据库表字段、收件人和数据量等资源/参数约束。
4. ALLOW、DENY、REQUIRE_APPROVAL 三态决策及稳定的原因码。
5. 审批请求与规范化请求摘要绑定；审批有有效期，执行凭证只能消费一次。
6. 文件读取、结构化数据库查询、模拟消息发送三类无真实副作用工具。
7. SQLite 审批状态、凭证消费状态与追加式审计事件。
8. 结构化测试集、自动化回归和指标统计。
9. 能现场复现正常放行、越权拒绝、审批后执行、篡改拒绝、重放拒绝和审计追踪。

### P1 应完成

- 一个轻量 FastAPI 接口或 CLI，能够发起请求、处理审批和查询审计链。
- 便于演示的简单本地页面；只有在 P0 稳定后再做。
- 10 至 20 个自然语言端到端场景，用于验证模型产生的调用仍受网关约束。

### 明确不做

- 真实邮件发送、真实生产数据库、云资源或真实个人数据。
- 自研或微调大模型。
- 生产级登录、OAuth、多租户、分布式部署、消息队列和通用策略语言。
- 用少量测试结果宣称达到生产级安全或合规认证。

## 2 推荐架构

```text
规则化生成器 / 可选模型适配器
                |
                v
        AgentGate Gateway
                |
   请求校验与规范化
                |
   RBAC + 资源/参数策略
        /       |       \
     DENY     ALLOW   REQUIRE_APPROVAL
       |         |          |
       |         |    审批 + 单次凭证
       |         |          |
       +---------+----------+
                 |
          受控工具执行器
                 |
       文件 / SQLite / 本地 outbox

所有阶段 -> SQLite 审计事件 -> trace_id 查询
```

关键约束：工具函数只向受控执行器注册；调用方、Agent、API 和 UI 都不能获得原始工具对象。

## 3 推荐仓库结构

```text
src/agentgate/
  models.py
  gateway.py
  normalizers/
  policy/
  approval/
  audit/
  executor/

  api/
policies/

tests/unit/
tests/integration/
tests/security_cases/
scripts/
docs/

```

先做可导入的核心库和测试，再加 API 或页面。这样 UI 变化不会破坏安全逻辑，也能在没有模型 API 时完成核心验收。

## 4 验收标准

### 功能验收

1. Analyst 对允许表执行 `db.select(limit=20)`，得到 ALLOW 和完整审计链。
2. Viewer 读取授权目录外文件或使用路径跳转，得到 DENY，底层工具调用计数不增加。
3. 高风险模拟外发在审批前不得执行；批准后只产生一条本地 outbox 记录。
4. 修改已批准请求的收件人或参数，摘要校验失败并拒绝执行。
5. 重复消费同一凭证或幂等键，不产生第二次副作用。
6. 按 `trace_id` 能还原请求、策略、审批、执行和结果事件。
7. 关键审计写入失败时安全失败，不调用工具。

### 量化目标

这些是验收目标，不是现有结果：

- 三态策略决策总体准确率不低于 95%。
- 高危攻击用例阻断或按预期转审批的比例不低于 95%。
- 必填审计字段完整率 100%。
- 网关内部 P95 附加延迟目标不超过 100 ms，不计模型生成、人工等待和工具自身耗时。
- 每个主要威胁类别至少 5 条测试，并覆盖阈值前后、空值、异常格式和重复请求。

## 6 当前第一批任务

按顺序完成，不并行铺开 UI 和模型接入：

1. 建立 `pyproject.toml`、`src` 布局与 pytest 基线。
2. 冻结五个核心数据契约和稳定原因码。
3. 定义工具注册表，禁止网关外部直接获得工具实现。
4. 实现规则化请求生成器和最小审计写入。
5. 实现文件路径规范化与目录边界测试。
6. 实现结构化 `db.select`，不接受任意原始 SQL。
7. 实现写入本地 outbox 的模拟消息工具。
8. 实现 RBAC 与资源/参数策略，先打通 ALLOW/DENY。
9. 加入审批状态机、摘要绑定与单次凭证。
10. 建立端到端安全用例和指标脚本。

完成第 1 至 8 项后，项目应已有可测试的基础网关闭环；第 9 项完成后才算具备课程方案中最关键的审批一致性与防重放能力。

## 7 风险与减配顺序

1. 模型接口不可用：使用规则化请求生成器，不影响核心验收。
2. 页面开发拖延：保留 CLI 或最小 FastAPI，取消复杂 UI。
3. 策略配置过重：使用 Python 加 JSON 配置，不引入通用策略平台。
4. 测试时间不足：先保证每类 5 条和关键边界，再增加自然语言场景。
5. 进度落后：先减可选模型、页面和性能可视化，不减“策略—审批—执行—审计”闭环。
