# AgentGate 项目定位、目标形态与实施路线

> 版本：2026-11-20（范围已收敛）
> 当前课程交付：本地 AgentGate MCP Server，而不是中央多用户网关。

## 当前范围说明

本文件最初讨论过中央网关、不同账户和 Local Connector 等产品化形态。经项目组确认，这些内容只保留为**远期展望**，不属于本课程当前实现范围。

当前项目的明确目标是：在一台电脑上将 AgentGate 注册为 Codex 可调用的本地 MCP Server；Codex 对 AgentGate 提供的文件、数据和模拟消息工具发起调用时，现有安全内核必须在真实工具执行前作出 `ALLOW`、`DENY` 或 `REQUIRE_APPROVAL` 决定，并生成审计记录。

实施细节以以下两份文档为准：

- [本地 MCP 场景与权限设计](LOCAL_MCP_SCENARIO.md)
- [本地 Codex MCP 接入指南](LOCAL_MCP_GUIDE.md)

## 1. 我们现在处于什么阶段

AgentGate 已完成“安全控制核心”的可运行原型，但尚未完成“真实 Agent 接入”。

当前已经具备：

- 接收结构化工具调用请求；
- 对请求进行角色、工具、资源范围、参数和风险判断；
- 返回 `ALLOW`、`DENY` 或 `REQUIRE_APPROVAL`；
- 将审批与原始请求摘要绑定，防止获批后篡改参数、复用凭证或重复执行；
- 通过受控的本地模拟工具执行文件读取、SQLite 查询和模拟消息发送；
- 用 SQLite 保存审批和审计记录，并提供网页控制台和 API；
- 80 个自动化测试通过。

当前尚未具备：

- 自然语言 Agent Loop；
- 真实 LLM Tool Calling 事件接入；
- MCP Server / MCP Gateway 适配层；
- 真实多用户认证；
- 对 Codex 内置 Shell、文件编辑等能力的全局拦截。

因此，当前网页是“网关核心验证台、审批台和审计台”，不是最终给业务用户输入自然语言的 Agent 产品。

## 2. 产品设想：Agent 的操作治理层

AgentGate 的核心不应是“限制某个文件能否读取”，而是：

> 当一个人把任务委托给 Agent 后，系统用独立于模型的规则决定 Agent 能否执行某项操作；高风险操作由人复核，并留下完整、可追溯的证据。

最终用户仍然在 Codex 或其他 Agent 中输入自然语言，例如“整理本周项目数据并导出摘要”。Agent 选择工具后，工具调用自动进入 AgentGate：

```text
用户自然语言
    ↓
Codex / 自建 Agent（任务规划、选择工具）
    ↓
AgentGate（认证、策略、风险、审批、审计）
    ↓
受控工具适配器（知识库、数据库、业务 API、模拟本地工具）
    ↓
实际资源或执行结果
```

网页只面向三类人员：

1. **审批人**：查看高风险请求并批准或拒绝；
2. **管理员**：登记工具、维护策略包和查看系统状态；
3. **审计人员**：按 `trace_id` 复核一次 Agent 任务的完整调用链。

## 3. 这是不是伪需求？

不是，但必须准确界定保护对象。

### 3.1 AgentGate 不保护什么

如果某位真人本来就能在电脑上直接打开某个文件，并主动绕过 Agent、自己阅读、复制或发送它，AgentGate **不能也不应该**阻止该真人。那是操作系统权限、文件系统 ACL、数据平台权限或企业 IAM 的问题。

如果所有资源都只是某个用户私有电脑上的普通文件，且该用户明确允许 Codex 直接读写整个目录，那么额外加一个网关的安全收益确实很低。课程报告必须如实承认这一点。

### 3.2 AgentGate 真正保护什么

AgentGate 管的是“**人向 Agent 委托的能力**”，即使该人自己有权查看资料，也未必希望 Agent：

- 因提示词注入或错误推理而批量导出资料；
- 读取与当前任务无关的大量内容；
- 修改数据库、删除记录或对外发送消息；
- 使用一个高权限服务账号做超出委托范围的操作；
- 在没有证据链的情况下执行高风险动作。

它的价值是把“模型猜测自己是否应该做”改为“网关用确定性规则判断是否允许做”。

一个真实的业务场景通常同时满足至少一项：

- 工具背后是共享知识库、数据库或业务 API，而不是私人文件夹；
- Agent 使用服务账号或受托凭据，权限可能大于单次任务所需；
- 导出、写入、外发、付款、删除等动作需要第二人审批；
- 组织需要知道“谁委托哪个 Agent 在何时访问了什么、依据哪条规则”；
- 资源本身还有底层权限系统，AgentGate 在其上再加一层面向 Agent 的动态约束。

### 3.3 不可绕过的前提

网关不是魔法拦截器。若想让某条工具调用无法绕过，必须让实际执行路径受网关控制：

- 数据库/API 只接受 AgentGate 持有的服务凭据；或
- 原始 MCP Server 只允许经网关访问；或
- 本地资源由独立的 Local Connector 执行，Connector 只接受网关签发的短期执行令牌；或
- 在操作系统、网络和数据服务侧同时限制直接访问。

因此，课程原型应准确表述为：**对“经 AgentGate 注册并暴露的工具路径”实施控制**，而不声称拦截任意 Codex 内置工具。

## 4. 什么是工具注册，什么是策略包

### 4.1 工具注册

工具注册不是授予权限，而是把一项可执行能力纳入网关管理目录。每个工具至少描述：

| 字段 | 示例 |
|---|---|
| 工具标识 | `knowledge.read_document` |
| 参数模式 | `document_id`、`section`、`purpose` |
| 资源类型 | 文档、记录、数据表、外部地址 |
| 风险级别 | 读、写、导出、外发、删除 |
| 上游适配器 | SQLite、模拟文件、业务 REST API、MCP Server |
| 安全限制 | 最大返回条数、允许字段、允许目标地址 |

### 4.2 策略包

策略包是一组可以复用的“工具目录 + 资源分类 + 风险规则 + 审批规则 + 审计字段”。

它可以是“科研知识库包”“校园业务包”“项目资料包”，医疗只是未来可能的一类，并非本项目必须选择的方向。

策略可以完全不依赖角色，例如：

```text
所有 export_summary：需要审批
所有 delete_record：默认拒绝
所有 send_message：仅允许测试域名，且需要审批
所有 read_public_document：直接允许
```

角色、用户归属、部门、访问目的、时间、设备、数据敏感等级等，都是策略可以选择使用的额外条件。

## 5. 中央网关与不同 Codex 账户分别是什么形态

### 5.1 课程演示的最小真实形态

```text
同学 A 的 Codex ── AgentGate Key A ─┐
同学 B 的 Codex ── AgentGate Key B ─┼── AgentGate 服务 ── 模拟工具
同学 C 的 Codex ── AgentGate Key C ─┘          │
                                                   ├── 审批网页
                                                   └── SQLite 审计
```

- **中央 AgentGate 服务**：运行在一台演示电脑或可访问的测试主机；它是策略、审批和审计的唯一事实来源。
- **每位同学的 Codex**：仍运行在各自电脑上，只是额外配置一个名为 `agentgate` 的 MCP 服务连接。
- **AgentGate Key**：三个不同的测试密钥，分别映射为三个固定身份。网关从密钥推导身份和角色，不能相信模型请求里自称的 `role`。
- **审批网页**：审批人登录后只能批准他人发起的请求；普通请求人没有审批入口。
- **模拟工具**：第一版继续使用项目中现有的文件、SQLite 和 outbox 模拟实现，避免真实系统风险。

这足以证明“不同人、不同 Agent、同一策略中心、同一审计链”的真实性。它不是企业 SSO，也不需要读取或共享三位同学的 OpenAI/Codex 账户密码。

### 5.2 未来产品化形态

生产系统可升级为：

```text
企业 SSO / OAuth ──→ AgentGate Policy Server
                              │
         ┌────────────────────┼────────────────────┐
         ▼                    ▼                    ▼
   MCP Gateway          API Adapter         Local Connector
   代理远程 MCP          代理业务系统         受控本地执行
```

- **Policy Server**：统一保存身份、策略包、工具目录、审批与审计；
- **MCP Gateway**：在 MCP `tools/call` 到达上游工具前执行策略；
- **API Adapter**：把非 MCP 的业务 API 包装为受控工具；
- **Local Connector**：安装在需要执行本地操作的主机上，只接受短期、绑定参数的执行令牌；
- **SSO/OAuth**：将组织成员身份传给网关，替代课程版固定 Key。

本项目只实现第一种形态，并将第二种作为架构展望。

## 6. 三人角色如何真实落地

建议课堂演示采用三种身份：

| 身份 | 作用 | 典型权限 |
|---|---|---|
| `analyst-a` | 请求人 | 查询、读取公开资料、申请导出 |
| `operator-b` | 业务操作人 | 调用受控业务操作，但高风险仍需审批 |
| `approver-c` | 审批人 | 批准/拒绝他人的高风险请求，查看审计 |

实现原则：

1. 客户端只携带密钥，不能自行提交可信角色；
2. 网关从密钥查出 `subject_id`、角色和状态；
3. 所有策略判断使用网关注入的身份上下文；
4. 不允许请求人审批自己的请求；
5. 审批后只允许执行“请求哈希完全一致”的那次操作；
6. 审计事件记录请求人、审批人、工具、参数摘要、决策和执行结果。

## 7. 实施路线与验收步骤

### 阶段 A：收紧现有身份边界

目标：让三人身份不是网页上可随意修改的字段。

1. 增加本地测试身份库：三枚随机测试 Key，对应三位固定身份；
2. 给 API 加认证中间件或依赖注入；
3. 从已验证身份填充 `subject_id` 和 `role`，忽略调用方提交的同名字段；
4. 审批 API 同样依据登录身份判断审批资格；
5. 新增测试：伪造角色、错误密钥、自己审批自己均失败；
6. 在网页增加“当前演示身份”提示，但不把它当作生产登录。

验收：同一请求即使把 JSON 中 `role` 改成 `approver`，也不会获得审批权限。

### 阶段 B：抽象工具目录与第一份策略包

目标：从写死的演示规则走向可说明的“可配置工具治理”。

1. 为现有三个模拟工具补齐工具元数据：名称、参数模式、资源类型、风险等级；
2. 新建一个通用策略包，例如 `project-data-demo`；
3. 定义资源标签：`public`、`internal`、`sensitive`；
4. 定义操作标签：`read`、`query`、`export`、`send`；
5. 配置规则：公开读取放行、敏感导出审批、未授权地址外发拒绝；
6. 将策略版本写入审计记录。

验收：能在文档和页面中解释“为什么这条规则命中”，而不只展示结果。

### 阶段 C：实现 MCP 接入适配层

目标：让真实 Agent 通过 MCP 自动进入现有网关。

1. 引入 Python MCP SDK；
2. 新增 `agentgate.mcp_server`，第一版只暴露三个模拟工具；
3. MCP 工具调用转换为现有 `ToolCallRequest`，再调用 `application.gateway.submit()`；
4. `DENY` 时返回结构化拒绝信息，且不调用上游模拟工具；
5. `REQUIRE_APPROVAL` 时创建审批记录，返回 `approval_id` 与“等待审批”状态；
6. 提供明确的 `approval_status` 或 `resume_approved_call` 工具，处理审批后的恢复；
7. 记录 MCP 调用与 AgentGate `trace_id` 的关联。

验收：MCP Inspector 或 Codex 的真实工具调用能在 AgentGate 审计时间线中找到。

### 阶段 D：接入 Codex 并进行端到端验证

目标：证明不是网页模拟，而是 Agent 工具调用进入了网关。

1. 在一台测试电脑的 Codex 中配置 AgentGate MCP 服务；
2. 先用 MCP Inspector 验证协议与三类结果，再用 Codex 验证 Agent 选择工具；
3. 完成三条固定演示链路；
4. 保留 Codex 调用记录、网关审计记录和模拟工具执行记录作为证据；
5. 明确测试“Codex 内置文件/Shell 工具是否绕过网关”，并如实记录边界。

三条验收链路：

| Agent 任务 | 预期决策 | 必须展示的证据 |
|---|---|---|
| 读取公开模拟资料 | `ALLOW` | MCP 调用、工具执行、审计链 |
| 读取受保护模拟资料 | `DENY` | 拒绝原因、上游执行计数为 0、审计链 |
| 发送模拟消息 / 导出摘要 | `REQUIRE_APPROVAL` | 待审批、批准前未执行、批准后只执行一次 |

### 阶段 E：报告、测试与演示材料

1. 新增身份认证、MCP 适配、审批恢复、绕过边界的自动化测试；
2. 统计策略正确率、应拦截操作拦截率、误拦截率、审计完整率、P95 延迟；
3. 截取一次完整审批与审计链作为报告案例；
4. 明确使用虚构数据和模拟工具，不作生产级安全声明；
5. 说明“经 AgentGate 注册的工具受到控制；Codex 内置工具不在本原型覆盖范围内”。

## 10. 范围控制：本项目不做什么

- 不接入真实医疗、学校或企业个人数据；
- 不发送真实邮件、不修改真实生产数据库；
- 不声称拦截 Codex 的所有内置工具；
- 不把简单静态 Key 说成企业级身份认证；
- 不在课程周期内实现企业 SSO、多租户、分布式策略同步或通用本地 Shell 代理。

这些边界不是缺点，而是让原型在有限时间内可运行、可测试、可诚实验收的必要条件。
