# AgentGate 证据边界与待确认决策

## 已确认事实

- 课程中期占总评 40%，期末验收占 60%。
- 期末需要现场演示系统、说明使用方法、技术方案、实际完成情况和人员分工。
- 现有材料已经形成题目、问题定义、总体架构、初步权限矩阵、三人分工、测试方向和演示场景。
- 当前代码目录在建立仓库前为空，没有可据此确认的程序实现、自动化测试或实验指标。
- 方案要求全部业务资源为本地虚构数据，并避免真实外部副作用。

## 材料之间的差异

| 主题 | 材料中的差异 | 当前建议 |
|---|---|---|
| 角色模型 | 中期报告使用“普通用户/管理员”；方案设计使用 Viewer、Analyst、Operator、Approver、Auditor | 采用五角色模型，能体现最小权限和职责分离 |
| 消息工具 | 材料中交替使用邮件、消息发送 | 统一内部名 `mail.send`，只写本地 outbox，界面可称“模拟消息发送” |
| 模型依赖 | 有的材料把 Tool Calling 作为主要入口，方案设计把它降为可选 | 规则化生成器必选，模型适配器可选 |
| 展示方式 | 讲稿考虑 Streamlit，方案允许 CLI 或简单页面 | 先完成核心库和 CLI/FastAPI，再决定是否加 Streamlit |
| 策略配置 | 材料提出 YAML 或 JSON | 先用 JSON，减少依赖；确有编辑需求再增加 YAML |
| 数据库调用 | 部分描述接近“SQL 查询” | 使用结构化查询对象，不接收任意原始 SQL |
| 时间计划 | 旧计划要求 11 月 8 日前已有 Agent Loop | 由于当前没有代码证据，从 11 月 12 日重新基线 |

## 当前推荐的工程决定

1. 核心是可导入的 Python 库，不从页面或模型 SDK 开始。
2. 工具注册表只暴露给受控执行器，防止调用方绕过网关。
3. 规范化后的请求使用稳定 JSON 序列化计算摘要。
4. 审批记录绑定主体、工具、规范化参数摘要和策略版本。
5. 凭证消费与执行开始使用同一个 SQLite 事务边界，验证单次消费。
6. 审计写入失败时采用 fail closed，不继续执行工具。
7. 对所有拒绝使用稳定原因码，便于测试和报告统计。
8. 把预期阈值与实际测量值分开保存，未跑实验前不填写结果。

## 开始编码前需要在首次实现中验证的假设

- 五角色模型是否与三位成员现有分工一致；角色是系统用户角色，不等同于项目组成员角色。
- `mail.send` 的软阈值和硬上限采用什么字段表达，避免为演示临时改接口。
- 审批人能否审批自己的请求；默认建议禁止自批。
- `idempotency_key` 是返回既有结果还是明确拒绝；默认建议同键同摘要返回既有结果，同键不同摘要拒绝。
- 目标环境统一支持的最低 Python 版本；材料建议 3.11+。

这些假设不需要先写长文讨论，可以通过数据模型、测试用例和一条架构决策记录直接固定。
